# نموذج Idempotency — ترحيل فاتورة المبيعات (Phase 7 Step C)

## 1. الآلية

بوّابة واحدة: `runTransaction` على `ledger/salesInvoices/{key}/status`.

```js
runTransaction(statusRef, current => (current === 'draft' ? 'posted' : undefined))
```

إرجاع `undefined` يُجهض المعاملة بلا كتابة. Firebase يُنفّذها **خادمياً** ويُعيد
المحاولة عند التعارض ⇒ من بين N طلب متزامن يلتزم **واحد فقط**. الباقون يحصلون على
`committed: false` ⇒ `DuplicatePostingError` ⇒ تترجمها الخدمة إلى نتيجة ناجحة
`alreadyPosted: true` تحمل القيد الأصلي — لا استثناء يصل للمستدعي.

**ليست** `if (!exists) create()` — وهو النمط الممنوع صراحةً.

## 2. لماذا حقل `status` لا سجل idempotency جديد

سجل منفصل يعني مجموعة RTDB جديدة ⇒ **تغيير مخطط** ⇒ ممنوع (§18). وحقل `status` موجود
أصلاً، ومحروس في `database.rules.json`، ويحمل بالفعل الدلالة المطلوبة. `idempotencyKey`
الذي تُعيده الخدمة (`salesInvoice:{key}:POST`) **وصفي** — للتتبّع والسجلّات، لا آلية
المنع. نفس قرار Phase 6/7-B.

## 3. ما هو مضمون

| الادّعاء | الإثبات |
|---|---|
| طلب مكرّر لا يُنتج قيداً ثانياً | `idempotency [2]` |
| ولا حركة مخزون ثانية | `idempotency [2]` · `inventory [4]` |
| ولا أثراً مالياً مضاعفاً (ذمّة · إيراد · ضريبة · مخزون) | `idempotency [4]` |
| 2 · 5 · 10 طلباً متزامناً ⇒ ترحيل أصلي **واحد بالضبط** | `idempotency [3]` |
| ولا استثناء غير مُصنَّف يصل للمستدعي | `idempotency [3]` |
| فاتورة مُرحَّلة سلفاً ⇒ نتيجة idempotent بالقيد القديم بلا كتابة | `idempotency [5]` |
| فشل ⇒ الحالة تعود `draft` ⇒ إعادة المحاولة تنجح بقيد واحد | `idempotency [6]` |
| 8 طلبات متزامنة ⇒ كمّية مخزون خارجة مفردة | `inventory [4]` |

## 4. حماية BUG-007

Phase 5 أثبتت أن القيود المكرّرة تُضاعف ميزان المراجعة بينما يبقى رصيد الطرف كما هو —
انفصال يصعب اكتشافه. الاختبار المضاد (`idempotency [4]`) يُثبت بعد **ترحيلين** للفاتورة
نفسها:

```
مجموع مدين دفتر اليومية = 23000  (لا 46000)
أثر ذمّة العميل (1130)   = 23000  مرّة واحدة
أثر الإيراد     (4100)   = 20000  مرّة واحدة
أثر الضريبة     (2140)   =  3000  مرّة واحدة
أثر المخزون              =      5  وحدات مرّة واحدة
```

## 5. الحدود المعروفة

1. **نافذة قراءة الرابط.** الحالة تنقلب بمعاملة، و`journalEntryKey` يُكتب في الكتابة
   الذرّية التالية. «الخاسر» قد يقرأ بينهما فيرى `posted` بلا رابط. الحلّ الحالي:
   استطلاع محدود (5 محاولات × 15ms) يُغلق النافذة عملياً — بلا ادّعاء حسم مطلق.
   لا قفل خادمي حقيقي متاح على خطة Spark.
2. **فشل الاسترجاع** يترك الفاتورة `posted` بلا قيد. إعادة المحاولة تُبلَّغ
   `alreadyPosted` بلا قيد مكرّر — لكن الإصلاح يدوي. مُختبَر في `failureInjection [K]`.
3. **الضمان يخصّ هذه الخدمة وحدها.** المسار القديم في `public/accounting.js` ما زال بلا
   قفل — الترحيل من الواجهة الحيّة يبقى عرضة لـBUG-007 حتى الوصل.
