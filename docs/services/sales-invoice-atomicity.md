# نموذج الذرّية — ترحيل فاتورة المبيعات (Phase 7 Step C)

> **المبدأ:** لا يُوصف شيء بأنه «ذرّي» إلا إن كان التنفيذ يضمنه فعلاً.

## 1. تصنيف كل عملية

| # | العملية | المسار | التصنيف | الضمان الفعلي |
|---|---|---|---|---|
| 1 | قراءة الفاتورة | `ledger/salesInvoices/{k}` | **READ-ONLY** | لا كتابة |
| 2 | قراءة شجرة الحسابات | `ledger/chartOfAccounts` | **READ-ONLY** | لا كتابة · **لا إنشاء** (فرق C1) |
| 3 | قراءة لقطة المخزون | `inventoryItems` · `inventoryMovements` · `warehouses` | **READ-ONLY** | لقطة واحدة ثابتة طوال الترحيل |
| 4 | مطالبة الحالة `draft → posted` | `ledger/salesInvoices/{k}/status` | **TRANSACTIONAL** | `runTransaction` خادمي — فائز واحد فقط |
| 5 | حجز رقم القيد | `ledger/counters/jrn/JV/{year}` | **TRANSACTIONAL** (منفصل) | ذرّي بذاته · **ليس** مع (7) |
| 6 | حجز أرقام حركات المخزون × N | `ledger/counters/invmov/out/{year}` | **TRANSACTIONAL** (منفصلة × N) | كلٌّ ذرّية بذاتها · **ليست** مع (7) |
| 7 | كتابة القيد + ربط الفاتورة + **كل** الحركات | `update(ref('/'), {...})` | **ATOMIC** | `update` واحد متعدّد المسارات — كل شيء أو لا شيء |
| 8 | استرجاع الحالة عند الفشل | `ledger/salesInvoices/{k}/status` | **COMPENSATED** (أفضل جهد) | قد يفشل هو نفسه — حدّ موثَّق |

**لا شيء مصنَّف NON-ATOMIC** في مسار النجاح: كل كتابة مالية ضمن (7).

## 2. محتوى الكتابة الذرّية الواحدة

```js
update(ref(db, '/'), {
  'ledger/journalEntries/{jid}'                  : journal,
  'ledger/salesInvoices/{k}/journalEntryKey'     : jid,
  'ledger/salesInvoices/{k}/journalEntryNumber'  : jrnNumber,
  'ledger/salesInvoices/{k}/postedAt'            : now,
  'ledger/salesInvoices/{k}/postedBy'            : uid,
  'ledger/inventoryMovements/{mid₁}'             : movement₁,
  …
  'ledger/inventoryMovements/{midₙ}'             : movementₙ
})
```

المفاتيح تُولَّد محلّياً بـ`push(ref)` بلا بيانات — لا كتابة قبل التحديث الذرّي.
`status` **لا يُعاد كتابته هنا** عمداً: إعادة كتابته تُخفي أي تغيير من طرف آخر بين
الخطوتين (نفس انضباط Phase 6/7-B).

## 3. مقارنة بالقديم

| | القديم (`postSInv`) | الجديد |
|---|---|---|
| قفل الحالة | ❌ لا يوجد (فحص على لقطة ذاكرة) | ✅ `runTransaction` |
| كتابة القيد | `push` منفصل | ضمن الكتابة الواحدة |
| ربط الفاتورة | `update` منفصل | ضمن الكتابة الواحدة |
| كتابة الحالة | `update` منفصل | ضمن معاملة الخطوة (4) |
| حركات المخزون | N × `push` منفصل، كلٌّ في `try/catch` يبتلع الخطأ | ضمن الكتابة الواحدة |
| **عدد نقاط الفشل بحالة جزئية** (3 أصناف) | **8** | **0** |

## 4. ما الذي يمكن أن يفشل — وماذا يبقى

| ما يفشل | الحالة المتبقّية | الاسترجاع | آمن لإعادة المحاولة؟ |
|---|---|---|---|
| مطالبة الحالة (4) | لا شيء تغيّر | — | ✅ |
| حجز رقم القيد (5) | حالة = `posted` | استرجاع تلقائي إلى `draft` | ✅ (رقم محروق فقط) |
| حجز رقم حركة (6) | حالة = `posted` + رقم قيد محروق | استرجاع تلقائي | ✅ |
| الكتابة الذرّية (7) | **لا كتابة مالية إطلاقاً** | استرجاع تلقائي | ✅ |
| الاسترجاع (8) نفسه | حالة `posted` **بلا قيد** | ❌ يدوي | ⚠️ لا قيد مكرّر، لكن يحتاج تدخّلاً |

السطر الأخير هو الحدّ الوحيد المتبقّي، وهو مُختبَر صراحةً
(`postSalesInvoice.failureInjection.test.mjs §[K]`) لا مفترَض.

## 5. لماذا لا ذرّية كاملة تشمل العدّادات

RTDB لا تدعم معاملة تشمل عدّة مسارات مع منطق قراءة-ثم-كتابة. `runTransaction` تعمل على
عقدة واحدة، و`update` متعدّد المسارات لا يقبل دوال. الجمع بينهما يتطلّب:
- Cloud Function معاملاتية ⇒ **يحتاج خطة Blaze** (المشروع على Spark)، أو
- مجموعة أقفال جديدة ⇒ **مخطط جديد، ممنوع صراحةً**.

الأثر الوحيد لهذا الحدّ **فجوة في الترقيم**، وهي بلا أثر على أي رصيد أو ميزان — ونفس
سلوك القديم حرفياً.
