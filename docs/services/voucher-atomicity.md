# الذرّية والتزامن في ترحيل السند — نموذج تعويضي (Saga)، لا ذرّية N+1 حرفية (Phase 7)

> يبني مباشرةً على `docs/services/atomicity.md` (Phase 6: كتابة واحدة
> متعدّدة المسارات لفاتورة واحدة). المشكلة الجديدة هنا: **عدد الفواتير N
> متغيّر**، وRTDB لا تدعم معاملة خادمية عبر مسارات متعدّدة اختيارية بحكم
> بنيتها — فالحل هنا مختلف بالضرورة، ويجب ألّا يُصوَّر كذرّية N+1 لأنه ليس
> كذلك. هذا الملف يوثّق بصراحة ما هو مضمون وما ليس مضموناً.

## لماذا لا ذرّية N+1 حرفية ممكنة

الكتابة الذرّية متعدّدة المسارات في Phase 6 (`update(ref(db,'/'), {...})`)
تعمل لأن **مجموعة المسارات معروفة مسبقاً وثابتة** (فاتورة واحدة + قيد واحد).
هنا، مجموعة المسارات تتضمّن N فاتورة **غير معروفة العدد إلا بعد قراءة
`voucher.allocations`**، وكل فاتورة تحتاج **فحصاً شرطياً** (هل التخصيص
يتجاوز رصيدها المتبقّي؟) لا كتابة غير مشروطة. RTDB's `update()` متعدّد
المسارات يكتب قيماً معروفة سلفاً — لا يستطيع تنفيذ منطق شرطي لكل مسار أثناء
الكتابة نفسها. الأداة الوحيدة القادرة على ذلك هي `runTransaction`، وهي
**تعمل على مسار واحد فقط لكل استدعاء**.

## النموذج الفعلي — ثلاث طبقات ضمان مختلفة

```
طبقة 1: بوّابة Idempotency على حالة السند
        runTransaction(status: draft→posted)  ← آمنة من التزامن فعلياً، مسار واحد

طبقة 2: تخصيص كل فاتورة — N معاملة مستقلّة، كل واحدة آمنة من التزامن بمفردها
        for (invoiceKey, amount) of allocations:
            runTransaction(invoicePath) { computeInvoiceAllocation(...) }
        ← كل معاملة فردية مضمونة خادمياً (Firebase يعيد المحاولة عند تعارض حقيقي)
        ← لكن التسلسل بين المعاملات (فاتورة 1 نجحت، فاتورة 2 تفشل) **ليس** ذرّياً بمعنى الكل-أو-لا-شيء الفوري

طبقة 3: الكتابة النهائية — قيد + ربط السند
        update(ref(db,'/'), {...})   ← ذرّية حرفية، نفس آلية Phase 6 تماماً
```

## ماذا يحدث عند فشل جزئي — التعويض الصريح (Saga)

إن نجحت التخصيصات 1..k ثم فشلت التخصيص k+1 (تجاوز رصيد، أو فاتورة غير
موجودة)، أو نجحت كل التخصيصات لكن فشلت الكتابة النهائية (طبقة 3):

```js
// FirebaseVoucherPostingRepository._compensateAllocations
for (const {invoiceKey, amount} of succeeded.slice().reverse()) {
    await runTransaction(invoicePath, current => ({
        ...current,
        paidAmount: round2(Math.max(0, current.paidAmount - amount))  // نفس منطق unallocateFromInvoices
    }));
}
await safeRollbackStatus(voucherPath, 'draft');
```

كل معاملة تعويض **آمنة من التزامن بمفردها** (نفس `runTransaction`)، لكن
**التسلسل الكامل ليس ذرّياً** — يوجد نافذة زمنية قصيرة، أثناء تنفيذ حلقة
التعويض، تكون فيها بعض الفواتير قد عادت لحالتها الأصلية والبعض الآخر لم
يُعوَّض بعد. هذا **مُوثَّق صراحةً هنا، لا مخفيّاً**:

| السيناريو | الضمان الفعلي |
|---|---|
| كل التخصيصات ثم الكتابة النهائية تنجح | ✅ اتساق كامل — الحالة النهائية صحيحة |
| تخصيص يفشل (تجاوز/فاتورة مفقودة) | ✅ اتساق نهائي مضمون (التعويض `best-effort` لكنه يعمل عملياً؛ كل خطوة معاملة حقيقية لا كتابة عمياء) — لكن **أثناء** التعويض نافذة قصيرة غير متّسقة |
| الكتابة النهائية تفشل (شبكة) بعد نجاح كل التخصيصات | نفس التعويض يُطبَّق — لا قيد يتيم، لا فاتورة معلَّقة بلا سبب |
| فشل التعويض نفسه (نادر جداً — نفس الاتصال الذي فشل للتوّ) | `best-effort` فقط — نفس سياسة `safeRollbackStatus` من Phase 6. **لا ضمان مطلق.** الفاتورة قد تبقى بمبلغ مخصَّص جزئياً بلا سند يربطها — أفضل من القديم (حيث لا تعويض إطلاقاً) لكن ليس مثالياً |

هذا مطابق حرفياً لتعليمات Phase 7 Step B: *«Distinguish clearly between:
Atomic commit... vs Concurrency-safe calculation... do not claim global
atomicity if the implementation does not actually provide it»*.

## نموذج التزامن — لماذا رفض التجاوز يعمل فعلياً تحت سباق حقيقي

كل معاملة تخصيص فردية تُنفَّذ عبر `runTransaction` على **عقدة الفاتورة
كاملة** (لا `paidAmount` وحده — الحساب يحتاج `grandTotal` أيضاً، وكلاهما
يجب أن يُقرآ من نفس اللقطة الذرّية):

```js
runTransaction(invoicePath, current => {
    const { nextPaidAmount } = computeInvoiceAllocation({
        invoiceKey, currentPaidAmount: current.paidAmount,
        grandTotal: current.grandTotal, allocatedAmount: amount
    });   // يرمي AllocationConflictError إن تجاوز — يُجهض المعاملة، بلا كتابة
    return { ...current, paidAmount: nextPaidAmount };
});
```

Firebase RTDB توثّق صراحةً: إن رمت دالة التحديث استثناءً، **تُجهَض
المعاملة بلا كتابة** والاستثناء يصعد للمستدعي — هذا ليس محاكاة، هو سلوك
المنصّة الفعلي. وإن تغيّرت قيمة الفاتورة بين القراءة ومحاولة الكتابة (تعارض
حقيقي من طرف آخر)، **يُعيد الخادم تنفيذ الدالة تلقائياً** بالقيمة الجديدة —
هذا ما يجعل رفض التجاوز صحيحاً حتى تحت سباق حقيقي، لا فحصاً على قراءة قديمة
قد تصبح خاطئة بحلول وقت الكتابة (نمط "افحص ثم اكتب" الممنوع صراحةً في
تعليمات Phase 6/7 كليهما).

**مُثبَت تنفيذياً لا افتراضاً** — `tests/services/postVoucher.allocation.test.mjs`
«السباق الحقيقي»: سندان مختلفان (6000 و7000) يحاولان التخصيص على نفس
الفاتورة (رصيدها 10000) عبر `Promise.all` حقيقي — النتيجة: **واحد فقط
ينجح**، الآخر يُرفَض بـ`AllocationConflictError`، والرصيد النهائي 6000 أو
7000 بالضبط — **أبداً 13000** (بخلاف القديم المُثبَت في
`tests/characterization/allocateToInvoices.test.mjs` الذي يقبل كليهما).

## نتيجة الاختبار — قبل مقابل بعد

| السيناريو | القديم (`allocateToInvoices`، مُثبَت) | الجديد (Phase 7، مُثبَت) |
|---|---|---|
| تجاوز رصيد فاتورة واحدة | 🔴 يُقبَل بلا فحص، بلا تحذير | ✅ `AllocationConflictError`، بلا كتابة |
| سباق حقيقي بين سندين على نفس الفاتورة | 🔴 كلاهما ينجح (13000 على فاتورة 10000) | ✅ واحد فقط ينجح — الآخر يُرفَض |
| فاتورة تخصيص غير موجودة | 🔴 `console.warn` ثم متابعة صامتة | ✅ `ValidationError` صريح، بلا كتابة |
| تخصيص جزئي ينجح ثم لاحق يفشل | (لا معادل — كتابات مستقلّة أصلاً) | ✅ تعويض عكسي لكل ما نجح، ثم `AllocationConflictError`/`AtomicityError` |
| فشل الكتابة النهائية بعد نجاح كل التخصيصات | (لا معادل) | ✅ تعويض كامل + `AtomicityError`، لا قيد يتيم |
