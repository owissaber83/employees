## 3. 🔴 أخطر اكتشاف — القيد قد لا يُنشأ والإشعار يمضي كأن شيئاً لم يكن

`createJournalForCreditNote` عند غياب حساب العملاء أو الإيرادات:

```js
if (!receivableAcc || !revAcc) { toast('⚠️ الإشعار سُجّل لكن تعذّر إنشاء القيد…', 'wn', 8000); return; }
```

تعود **بلا قيمة**. و`submitCreditNote` (:16112) تستدعيها هكذا:

```js
await createJournalForCreditNote(cnRef.key, cnData);   // ← لا فحص للنتيجة إطلاقاً
await createReturnMovementsForCN(cnRef.key, cnData);
… await update(ref(db, 'ledger/salesInvoices/' + key), upd);   // creditedAmount / fullyCredited
```

فيمضي المسار كاملاً: المستند مكتوب، المخزون أُعيد، و`creditedAmount`/`fullyCredited`
مُحدَّثان — **بلا أي قيد محاسبي**. نفس البنية حرفياً في `submitDebitNote` (:16249).

هذا يُخالف انضباط `postSInv` التي تفحص `if (!jrnRef) … return;` قبل تثبيت الترحيل.

**الأثر المالي:** `calcCustomerBalance` (:12280–12283) تُنقص الرصيد بـ`creditedAmount`
وتستبعد الفاتورة كلياً عند `fullyCredited`، بينما دفتر الأستاذ لم يتغيّر ⇒ **رصيد العميل
يُظهر الخصم وميزان المراجعة لا يُظهره**. نفس نمط الانفصال في BUG-007 لكن بالاتجاه
المعاكس، ومع تنبيه `wn` عابر فقط. مُسجَّل كـ**BUG-010**.

## 5. القيد الفعلي — والفرق الجوهري بين المسارين

**الإشعار الدائن** (عكس فاتورة مبيعات):
```
مدين   الإيرادات (salesAccountCode ‖ 4100)  = netBeforeTax × fx  (+ فرق التقريب)
مدين   ضريبة المخرجات (2140)                = vatTotal × fx      [إن > 0 والحساب موجود]
دائن   العملاء (custReceivableAccount)      = grandTotal × fx
```
تسوية التقريب على `lines[0]` (الإيراد)، محسوبة من **مجموع المدين**.

**الإشعار المدين** (عكس فاتورة مشتريات):
```
مدين   الموردون (vendPayableAccount)        = grandTotal × fx
دائن   المصروف (expenseAccountCode ‖ 5110)  = netBeforeTax × fx  (+ فرق التقريب)
دائن   ضريبة المدخلات (1180)                = vatTotal × fx      [إن > 0 والحساب موجود]
```
تسوية التقريب على `lines[1]` (المصروف)، محسوبة من **مجموع الدائن**.

**عند غياب حساب الضريبة** يُضمّ مبلغها إلى سطر الإيراد (CN) أو المصروف (DN) — نفس نمط
«آخر ملاذ» في فاتورة المبيعات، بلا تنبيه صريح هنا.

### فروق مؤكَّدة بين CN وDN (ليسا متماثلين)

| الجانب | Credit Note | Debit Note |
|---|---|---|
| حساب الضريبة | `2140` (مخرجات) | `1180` (مدخلات) |
| حساب الطرف | `custReceivableAccount()` | `vendPayableAccount()` |
| الحساب المقابل | `salesAccountCode ‖ 4100` | `expenseAccountCode ‖ 5110` |
| مصدر الحساب المقابل | `inv.salesAccountCode` | `inv.debitAccountCode` ‖ `getExpenseAccountForType(inv.expenseType)` ‖ `'5110'` |
| اتجاه المخزون | `in` (عودة للمخزن) | `out` (رجوع للمورد) |
| **تكلفة حركة المخزون** | `calcInvItemMovingAvg().avgCost` ← `item.costPrice` ← `line.unitPrice` ← 0 | **`parseFloat(line.unitPrice) ‖ 0` مباشرةً — بلا متوسط متحرّك إطلاقاً** |
| سطر التقريب | `lines[0]` من مجموع المدين | `lines[1]` من مجموع الدائن |

فرق التكلفة **منطقي لا سهو**: سطر فاتورة المبيعات يحمل سعر **البيع** فيلزم المتوسط
المتحرّك للتكلفة، بينما سطر فاتورة المشتريات يحمل سعر **الشراء** أصلاً. يُحفظ كما هو.

### ما لا يفعله القديم — ولا يجوز إضافته

- **لا عكس للاحتجاز (1131)** ولا **للدفعة المقدمة (2150)** حتى لو حملتهما الفاتورة الأصلية.
- **لا قيد تكلفة بضاعة مباعة** — متّسق مع نتيجة Step C (جرد دوري لا مستمر).
- **لا فحص كفاية رصيد** قبل حركة الخروج في DN (بخلاف فاتورة المبيعات التي تُحذّر).

الأول قرار محاسبي معلّق (**D3**)، والثاني مُسجَّل سابقاً (**D2**)، والثالث سلوك محفوظ (A).

## 6. حساب المبالغ — عائق معماري حقيقي

`cnCompute`/`dnCompute` **تقرآن كميات الإرجاع من DOM** مباشرةً:

```js
const rq = document.getElementById('cnQty' + i);
const retQty = rq ? Math.min(origQty, Math.max(0, parseFloat(rq.value) || 0)) : origQty;
```

منطق مالي حقيقي (نسبة الخصم الرأسي `hdrRatio` · تناسب السطر · حساب الضريبة · التقريب)
مدفون في طبقة العرض. **لا يمكن استدعاؤه بلا DOM.**

⇒ الدالة النقيّة الجديدة يجب أن تستقبل `returnQuantities` كوسيط صريح، ويُثبَّت التطابق مع
القديم بحقن DOM وهمي في المِشجب (نفس أسلوب حقن `window` في المراحل السابقة). هذا الفرق
تمثيلي بحت (**B**) لكنه يغيّر شكل الواجهة البرمجية، فيُعلَن صراحةً لا يُمرَّر بصمت.

## 7. Idempotency — تحليل §9 قبل أي تصميم

**لا يوجد أي حاجز في القديم:** المستند يُنشأ بـ`push` بمفتاح جديد كل مرّة، و`status`
يُكتب `'posted'` ثابتاً عند الإنشاء. لا `draft`، لا claim، لا فحص تكرار. نقر مزدوج ⇒
**إشعاران كاملان**: مستندان، قيدان، حركتا مخزون، وتحديثان على الفاتورة.

وأسوأ: تحديث الفاتورة **قراءة-ثم-كتابة من لقطة الذاكرة**:
```js
const prevCredited = parseFloat(inv.creditedAmount) || 0;      // من اللقطة
const keys = Array.isArray(inv.creditNoteKeys) ? … : …;        // من اللقطة
… upd.creditedAmount = round2(prevCredited + c.grandTotal);
```
إشعاران متزامنان يقرآن `prevCredited` نفسه ⇒ **ضياع تحديث**: `creditedAmount` يعكس
واحداً فقط، و`creditNoteKeys` يفقد مفتاحاً. مُسجَّل كـ**BUG-012**.

### هل يمكن حاجز آمن **بلا مخطط جديد**؟ — نعم، بشرط

فُحصت الخيارات الأربعة المطلوبة في §9:

| الخيار | صالح؟ | السبب |
|---|---|---|
| `existing status` على المستند | ⚠️ **جزئياً** | `status` موجود فعلاً، لكن المستند يُنشأ بمفتاح جديد كل نداء فلا شيء يُطالَب |
| `existing document key` | ✅ **نعم — إن ولّده المستدعي** | مفتاح `push` يُولَّد **محلّياً بلا كتابة**؛ لو مرّره المستدعي صار هويّة ثابتة قابلة للمطالبة |
| `credit/debit note identity` | ❌ | لا حقل هوية طبيعي (الرقم نفسه غير موثوق — BUG-011) |
| `deterministic posting key` | ❌ | يتطلّب تخزينه ⇒ مجموعة جديدة ⇒ ممنوع |

**التصميم المقترح (بلا حقل جديد ولا مجموعة جديدة):**
`runTransaction` على `ledger/creditNotes/{noteKey}/status` بدلالة **«اخلق إن غاب»**:
`current === null ? 'posted' : undefined`. أوّل نداء يلتزم، والمكرّر بنفس `noteKey`
يُجهَض ⇒ `DuplicatePostingError`. نفس آلية Phase 6/7 حرفياً، لكن المطالبة **بالإنشاء**
لا بـ`draft→posted`.

⚠️ **ما يغيّره هذا في العقد:** المستدعي يجب أن يولّد `noteKey` (عبر `push(ref).key`)
ويعيد استخدامه عند إعادة المحاولة. هذا **تغيير في واجهة الاستدعاء لا في المخطط** — يبقى
قراراً معروضاً عليك قبل التنفيذ.

**الحاجز الثاني، وهو الأهمّ مالياً:** `runTransaction` على عقدة الفاتورة المصدر نفسها
لتحديث `creditedAmount`/`creditNoteKeys`/`fullyCredited` ذرّياً — يُغلق ضياع التحديث
(BUG-012) ويُمكِّن رفض التجاوز. نفس نمط `computeInvoiceAllocation` في Phase 7-B تماماً.

## 8. التجاوز (Over-credit / Over-debit) — §19

**سلوك القديم المُتحقَّق منه:** `cnCompute` تحدّ كل سطر بكمّيته الأصلية، فإشعار واحد لا
يتجاوز الفاتورة. لكن **الإشعار الثاني يقرأ سطور الفاتورة الأصلية من جديد** لا المتبقّي.
السيناريو الفعلي:

```
فاتورة 10,000 → إشعار دائن جزئي 6,000  ⇒ creditedAmount = 6,000
              → إشعار دائن ثانٍ بكامل الكميات = 10,000
                 isFull = (6,000 + 10,000) ≥ 10,000 − 0.01  ⇒ صحيح
                 ⇒ creditedAmount = 10,000 (مقصوص!) · fullyCredited = true
                 ⇒ لكن القيد يعكس 10,000 كاملة
النتيجة في الدفتر: 10,000 مدين − 6,000 − 10,000 = ذمّة عميل **سالبة 6,000**
```

⇒ **الحقل مقصوص، والدفتر متجاوَز.** انفصال جديد بين الشاشتين. مُسجَّل كـ**BUG-013**.

نيّة النظام واضحة من الحراسات (`!fullyCredited` + حدّ الكمّية) أن التجاوز **غير مقصود**،
لكن التنفيذ يسمح به. الخدمة الموازية سترفضه ذرّياً — نفس ما فُعل مع BUG-008 في Phase 7-B،
وبنفس التصنيف (**C**). لن يُطبَّق شيء على القديم.

## 9. قواعد الأمان — تغطية أضعف (توثيق، لا تعديل)

`ledger/creditNotes` و`ledger/debitNotes` و`ledger/inventoryMovements` **غير مذكورة
إطلاقاً** في `database.rules.json`؛ تسقط تحت القاعدة العامة `$other`: أي عضو في المستأجر
يقرأ ويكتب، بلا تحقّق حقول ولا حارس حالة ولا منع تعديل. بالمقابل `salesInvoices`
و`purchaseInvoices` تحملان قواعد أدقّ.

**لا تعديل على القواعد في هذه المرحلة** (ممنوع صراحةً). يُسجَّل كحدّ معروف، وله أثر عملي
واحد على التصميم: الكتابة الذرّية ستشمل مسار الفاتورة الأخضع لقواعد أصرم — وهو وضع سبق
اختباره في Step C.

## 10. الخلاصة — لا شرط توقّف تقني

- ✅ لا حاجة لتغيير مخطّط: الذرّية ممكنة بـ`update` واحد متعدّد المسارات يضمّ
  المستند + القيد + الفاتورة + كل الحركات.
- ✅ الحاجز ضدّ التكرار والتجاوز ممكن بمعاملتين على عقدتين **موجودتين** أصلاً.
- ⚠️ العدّادات (`jrn` · `invmov`) تبقى خارج الذرّية — نفس حدّ Step C الموثَّق.
- ⚠️ رقم CN/DN نفسه سيتحوّل إلى حجز بمعاملة على عدّاد **من نفس عائلة `counters` القائمة**
  (`ledger/counters/cn/{year}`) — مسار جديد داخل مجموعة قائمة، لا مجموعة جديدة.
  **هذا القرار معروض عليك** لأنه يغيّر مصدر الترقيم عن القديم (فرق C).
- 🔴 أربعة عيوب جديدة مُوثَّقة: BUG-010 · BUG-011 · BUG-012 · BUG-013.
- 🔴 قرار محاسبي معلّق جديد: **D3** (عدم عكس الاحتجاز والدفعة المقدمة).
