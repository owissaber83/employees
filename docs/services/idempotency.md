# Idempotency — لماذا لا سجل جديد، وكيف يُحسم التزامن الحقيقي (Phase 6)

## القرار الحاسم — لا مجموعة `ledger/postingLocks/*` جديدة

المطلوب بحث ما إن كان إدخال سجل idempotency ممكناً **دون تغيير المخطّط**
قبل تصميم أي مجموعة جديدة (§9). النتيجة: **ممكن تماماً — بلا أي حقل أو
مجموعة جديدة.**

`ledger/purchaseInvoices/{key}/status` **موجود أصلاً**، بقيمتين معروفتين
(`'draft'`/`'posted'`) يقرأهما ويكتبهما القديم اليوم. الانتقال من `'draft'`
إلى `'posted'` **هو نفسه** حدث "تمّ الترحيل" — لا حاجة لتمثيله في مكان ثانٍ.

```
مصفوفة القرار:
  سجل idempotency منفصل (ledger/postingLocks/*)  → مجموعة جديدة → §9 STOP → موافقة مطلوبة
  معاملة على status الحقل الموجود                → لا تغيير مخطّط → لا STOP → 🟢 هذا المُختار
```

**لم يُطلب schema change. لم تُلمَس `database.rules.json`.** القرار موثَّق
هنا بدل تنفيذه بصمت، تماماً كما طلبت التعليمات (§9، §26).

## المفتاح — وصفي، لا آلية الحسم الفعلية

```js
buildIdempotencyKey({ sourceType:'purchaseInvoice', sourceId:key, operation:'POST' })
// → 'purchaseInvoice:{key}:POST'
```

حتمي، بلا طابع زمني، بلا UUID (§8 صراحةً). **لكنه لا يُخزَّن ولا يُقارَن به
أي شيء فعلياً في هذا الإصدار** — هو مُعرِّف وصفي يُعاد في نتيجة الخدمة
للتتبّع/التسجيل، بينما **آلية المنع الفعلية** هي معاملة `status` أدناه. هذا
موثَّق صراحةً في `src/services/accounting/idempotency/idempotencyKey.js`
كي لا يُفهَم خطأً أن المفتاح نفسه هو ما يمنع التكرار.

## الآلية الفعلية — معاملة خادمية، لا `if(!exists) create()`

```js
const claim = await runTransaction(
    ref(db, `ledger/purchaseInvoices/${key}/status`),
    current => current === 'draft' ? 'posted' : undefined   // undefined = تراجع، لا كتابة
);
if (!claim.committed) { /* مُرحَّلة بالفعل — لا كتابة إضافية */ }
```

`runTransaction` في Firebase RTDB **خادمية**: تُرسِل القيمة الحالية،
والخادم يُعيد المحاولة تلقائياً إن تغيّرت القيمة بين القراءة والكتابة —
هذا بالضبط ما ينفي نمط "افحص ثم اكتب" غير الآمن (§8 يمنعه صراحةً بالاسم).
**ليست محاكاة، هي الآلية الحقيقية التي توفّرها المنصّة.**

## نتيجة الطلب المكرَّر

```js
{ success: true, alreadyPosted: true, journalId, journalNumber, sourceId, idempotencyKey }
```

**ليس خطأً.** المستدعي (شاشة، أو مهمّة مؤتمتة تُعيد المحاولة) يحصل على نفس
النتيجة التي كان سيحصل عليها لو نجح هو أوّلاً — هذا هو تعريف Idempotent
عملياً، لا مجرّد "رفض الطلب الثاني".

## 🔴 حدّ حقيقي مُكتشَف بالاختبار — نافذة سباق على القراءة اللاحقة

أول تصميم لهذا المستودع قرأ الفاتورة فوراً بعد فشل المطالبة، ليُرجع
`journalId` الأصلي للخاسر. **اختبار التزامن الحقيقي (`Promise.all`) كشف
عطلاً فعلياً**: الخاسر قد يقرأ الفاتورة *بعد* أن ينقلب `status` (بمعاملة
مستقلّة) *لكن قبل* أن يكتب الفائز `journalEntryKey` (ضمن التحديث الذرّي
اللاحق) — نافذة حقيقية، ميلي ثوانٍ، لكنها حقيقية.

**لا حلّ مثالي متاح على RTDB بلا دالة خادمية** (Cloud Functions معطَّلة على
خطة Spark — §21 من الوضع الحالي). التنفيذ الحالي: محاولات محدودة (5) بتأخير
قصير (15ms) تنتظر ظهور `journalEntryKey` قبل أن تستسلم وتُعيد
`original: null`:

```js
// FirebaseJournalPostingRepository._pollForPostedLink
for (let i = 0; i < attempts; i++) {
    const v = (await get(...)).val();
    if (v.status !== 'posted') return v;
    if (v.journalEntryKey) return v;
    if (i < attempts - 1) await sleep(delayMs);
}
return null;
```

**هذا موثَّق صراحةً كحدّ لا كحلّ نهائي (§8: «وثّق القيد بدل التظاهر بحلّه»).**
تحت حمل استثنائي (الفائز بطيء جداً لأي سبب) قد يعود الخاسر بـ
`journalId: null` رغم أن الترحيل **نجح فعلاً** — الفاتورة تكون `posted`
لكن الاستجابة لا تحمل رقم القيد. **لا تكرار في هذه الحالة على أي حال** —
الخطر الوحيد هو معلومة ناقصة في الاستجابة، لا ازدواج في الكتابة.

## مُثبَت تنفيذياً — لا افتراضاً

`tests/services/postPurchaseInvoice.idempotency.test.mjs` (16 تأكيداً):

| السيناريو | النتيجة |
|---|---|
| نفس الطلب مرّتين تتابعياً | الثاني `alreadyPosted`، نفس `journalId` |

## ما هذا لا يحلّه — BUG-006 (`ensureStdAccount`)

`ensureStdAccount` **غير مُستدعاة** في مسار فاتورة المشتريات (راجع
`docs/services/posting.md`) — BUG-006 لا يُصلَح هنا، ولا يمسّ هذا المسار
أصلاً. أي مسار مستقبلي يستدعيها (فاتورة المبيعات) يحتاج معالجة idempotency
خاصة به — نفس نمط `status`، لكن على حساب لا على مستند (§22 يمنع صراحةً
إعادة التصميم العام لها الآن).
