# نموذج Idempotency — الإشعار المدين (Phase 7 Step D)

> ⚠️ **النموذج مطابق حرفياً لنظيره الدائن** (نفس المحرّك بإعدادات مختلفة).
> المرجع الكامل: [`credit-note-idempotency.md`](credit-note-idempotency.md).

## 1. المشكلة التي لم تكن موجودة في الفواتير

الفواتير تملك `status: 'draft'` سابقاً على الترحيل، فالمطالبة انتقال (`draft → posted`).
**الإشعار لا يملك ذلك:** القديم يُنشئه بـ`push` بمفتاح جديد كل نداء، بحالة `posted`
مباشرةً. لا شيء يمكن المطالبة به ⇒ **صفر حماية** من التكرار.

## 2. الحلّ المُوافَق عليه (قرار المالك رقم 1)

**مرساة الهوية ينتجها المستدعي:**

```js
const noteKey = push(ref(db, 'ledger/debitNotes')).key;   // محلّي — لا يكتب شيئاً
await postDebitNote({ noteKey, invoiceKey, returnQuantities });
```

**المطالبة معاملة خادمية على حقل `status` الموجود** — لا حقل جديد، لا مجموعة جديدة:

```js
runTransaction(ref(db, `ledger/debitNotes/${noteKey}/status`),
    current => (current == null ? 'draft' : undefined));
```

| الحالة الحالية | النتيجة |
|---|---|
| غائبة | `'draft'` ⇒ **نملك المطالبة** |
| `'draft'` | إجهاض ⇒ ترحيل متزامن جارٍ، أو محاولة سابقة لم تُحرَّر |
| `'posted'` | إجهاض ⇒ `alreadyPosted` مع القيد الأصلي |

الانتقال `draft → posted` يقع في **الكتابة الذرّية النهائية** (المستند يُكتب كاملاً
بحالة `posted`). إرجاع `undefined` يُجهض المعاملة خادمياً بلا كتابة — **ليست**
`read → if not posted → write`، وهو النمط الممنوع صراحةً.

## 3. ما هو مضمون

| الادّعاء | الإثبات |
|---|---|
| نفس `noteKey` مرّتين ⇒ مستند واحد · قيد واحد · حركات واحدة | `idempotency [2]` |
| ولا يتضاعف أثر الفاتورة ولا يتكرّر المفتاح في المصفوفة | `idempotency [2]` |
| 2 · 5 · 10 نداءً متزامناً بنفس المفتاح ⇒ **إصدار أصلي واحد بالضبط** | `idempotency [3]` |
| مفاتيح مختلفة ⇒ إشعارات مختلفة مشروعة (بلا ضياع تحديث) | `idempotency [4]` |
| `noteKey` مفقود ⇒ رفض صريح | `idempotency [5]` |
| إعادة المحاولة بعد فشل بنفس المفتاح تنجح (المطالبة حُرِّرت) | `atomicity [3]` |

## 4. حدّ صريح — ما **ليس** مضموناً

**تكرار الطلب بمفتاح جديد ليس تكراراً.** إشعاران بنفس المبالغ ومفتاحين مختلفين =
إشعاران مشروعان، وسيُقبلان ما دامت السعة تتّسع. لا توجد هوية طبيعية أخرى للإشعار
(الرقم غير موثوق في القديم — BUG-011)، وأي مفتاح حتمي مشتقّ من المحتوى يستلزم تخزينه
⇒ **مجموعة جديدة ⇒ ممنوع**.

⇒ **مسؤولية المستدعي:** توليد `noteKey` مرّة واحدة عند فتح الشاشة، وإعادة استخدامه في
كل إعادة محاولة. هذا هو الشرط الذي يجعل الضمان أعلاه صحيحاً.

**حدّان إضافيان:**
1. فشل تحرير المطالبة ⇒ عقدة `draft` عالقة تمنع إعادة المحاولة بنفس المفتاح (يلزم مفتاح جديد).
2. نافذة قراءة الرابط: «الخاسر» قد يقرأ قبل اكتمال كتابة «الفائز» — يُغلقها استطلاع
   محدود بلا ادّعاء حسم مطلق (لا قفل خادمي على خطة Spark).

## 5. الضمان يخصّ الخدمة وحدها

`submitDebitNote` القديمة ما زالت بلا أي حماية — النقر المزدوج عليها في الواجهة الحيّة
ينتج إشعارين. **لم تُعدَّل ولن تُعدَّل في هذه المرحلة.**
