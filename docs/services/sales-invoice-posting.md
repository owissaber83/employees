## 2. الاستخدام

```js
const post = createPostSalesInvoiceService({
    chartOfAccountsRepo, salesInvoicePostingRepo,
    getInvoice, getCustomer, getInventorySnapshot,
    cfg: { baseCurrencyCode: 'SAR', arApMode: 'aggregate' },
    currentUser: { uid }

const r = await post({ invoiceKey });
// { success, journalId, journalNumber, movementIds, movementNumbers,
//   alreadyPosted, idempotencyKey, warnings }
```

`getInventorySnapshot()` تُعيد `{items, movements, warehouses}` — لقطة واحدة ثابتة
تُستخدم طوال التخطيط، تماماً كما يعتمد القديم على لقطة `window.inventory*`.

## 3. القيد المُنتَج

مطابق حرفياً للقديم (41 تأكيداً في `tests/golden-master/sales-invoice.test.mjs`):

```
مدين   العملاء (1130 / حساب المجموعة)   = (الإجمالي − الاحتجاز) × سعر الصرف
مدين   محتجزات ضمان (1131)              = الاحتجاز × سعر الصرف        [> 0.005]
مدين   دفعات مقدمة من العملاء (2150)     = المسترد × سعر الصرف         [> 0.005]
دائن   الإيرادات (salesAccountCode ‖ 4100) = الصافي قبل الضريبة (+ فرق التقريب)
دائن   ضريبة المخرجات (2140)             = الضريبة × سعر الصرف         [> 0]
إجمالي القيد = (الإجمالي + المسترد) × سعر الصرف
```

**لا سطر مخزون ولا تكلفة بضاعة مباعة** — النظام جرد دوري: المشتريات تُصرَف مباشرة،
والمخزون يُتابَع كمّياً/قيمياً في `inventoryMovements` فقط. سياسة قائمة، لا تُغيَّر هنا.

## 5. الحدود المعروفة

1. **العدّادات خارج الذرّية.** فشل بعد حجز رقم ⇒ فجوة ترقيم (لا أثر مالي). نفس القديم.
2. **فشل الاسترجاع بعد فشل الكتابة الذرّية** يترك `status='posted'` بلا قيد — الفاتورة
   «مقفلة» وتحتاج تدخّلاً يدوياً. لا يُنتج قيداً مكرّراً (مُختبَر: `failureInjection [K]`).
3. **نافذة استطلاع الرابط**: «الخاسر» في سباق حقيقي قد يقرأ قبل اكتمال كتابة «الفائز» —
   استطلاع محدود يُغلقها عملياً بلا ادّعاء حسم مطلق (لا قفل خادمي على خطة Spark).
4. **الخدمة لا تُطبّق ضوابط الواجهة**: الصلاحيات · حد الاعتماد · الإيقاف الائتماني ·
   الحد الائتماني · قفل الفترة. كلها في `postSInv` القديمة وتبقى مسؤولية المهايئ.
5. **لا نسخة من مسار «تعديل فاتورة مرحّلة»** (`saveSInv`) ولا `unpostSInv` — خارج Step C.

## 6. الأداء

`npm run svc:sales:perf`. أرقام **حساب نقيّ في الذاكرة**، لا زمن RTDB:

| المكوّن | ms/استدعاء |
|---|---|
| بناء القيد | ~0.0003 |
| التحقّق البنيوي | ~0.00004 |
| فحص التوازن | ~0.00009 |
| تخطيط حركة واحدة (200 حركة تاريخية) | ~0.049 |
| الخدمة الكاملة (سطر واحد، محاكي) | ~0.12 |

**زمن الإنتاج الفعلي** تحكمه ذهابات/إيابات الشبكة: `1` معاملة حالة + `1` معاملة عدّاد
قيد + `N` معاملة عدّاد حركة + `1` كتابة ذرّية = **(3 + N)** — والحساب النقيّ أعلاه مهمَل
أمامها. تخطيط المخزون خطّي في السطور ويمسح سجل الحركات لكل سطر (O(سطور × حركات)) —
منقول حرفياً من القديم، ولا يُحسَّن في مرحلة الاستخلاص.
